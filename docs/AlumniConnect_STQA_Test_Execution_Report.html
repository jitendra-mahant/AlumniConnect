2. Project and Test Scope

AlumniConnect is a web platform connecting students, alumni, teachers and administrators. The selected repository tests cover only the behaviors explicitly asserted by the five executed scripts.

In scope for this execution

  • Font/theme wiring and typography configuration through source assertions.
  • Sidebar and mobile-drawer structure, keyboard affordances, and responsive breakpoint class presence through source assertions.
  • Configured demo-account roles, bcrypt behavior, institutional email examples, LinkedIn URL normalization, and profile privacy sanitization.
  • 2022 alumni dataset size and selected data normalization/privacy behavior.
  • Duplicate-registration normalization and response/data-preservation scenarios, including the script's explicitly simulated cases.

Not covered by this execution

  • Live API workflows, persisted database behavior, database migration/seeding, or production data.
  • Real browser rendering at viewport sizes; the responsive checks inspect source/class strings rather than opening a browser.
  • Actual SMTP connection or email delivery, load/performance testing, accessibility automation, and manual exploratory testing.
  • Any test script not listed in Section 3. No new test cases were invented or executed.
The backend package defines a smoke-test command that reseeds a database and can fall back to the configured MongoDB URI. It was intentionally not run to avoid changing local or live data. SMTP and database integration scripts were also excluded from this non-destructive run.

5. Findings and Defect/Discrepancy Log

The existing typography tests were not modified. Findings below preserve their literal outcomes and distinguish a failed test assertion from a confirmed runtime defect.

IDEvidenceFindingRecommended disposition
F-01 TC-TYP-01, TC-UI-05 Both scripts expect a Helvetica font option. The current theme configuration instead exposes Arial, Roboto and Times variants, so both assertions fail. Confirm the approved font requirement. Then align either the implementation or the two test expectations and rerun those tests.
F-02 TC-TYP-03 The pre-hydration check expects the exact stack 'Times New Roman', Times, serif; the current stack includes an additional Georgia fallback. This is an exact-stack mismatch, not absence of Times New Roman. Decide whether the fallback is allowed and make the expected stack consistent in the source and test.
F-03 TC-TYP-08 The test rejects any Roboto reference, while the current theme and CSS intentionally include Roboto. The assertion therefore fails against the current configuration. Resolve the font policy and update implementation or test rule accordingly; do not mark the assertion passed until rerun.
Classification: The above are verified test failures and source/test expectation discrepancies. The tests alone do not establish whether the current font choices are acceptable product behavior; that decision depends on the approved typography requirement.

6. Quality Summary, Limitations and Next Actions

Measured results

  • Execution rate: 32 / 32 listed cases executed = 100% for this selected set.
  • Pass rate: 28 / 32 executed cases passed = 87.5%.
  • Open failed cases: 4 typography assertions (TC-TYP-01, TC-TYP-03, TC-TYP-08 and TC-UI-05).
  • Not run: No unexecuted case is counted as a pass. Database/API smoke, SMTP, realtime and other integration scripts are outside this run.

Limitations

  • Several suites validate source strings or local helper logic, not the running browser application.
  • Duplicate-registration scenarios include in-memory simulations and do not verify a database-backed controller response.
  • Responsive breakpoints were checked as class-name presence, not by viewport screenshots or browser automation.
  • There is no claim of full requirements coverage, performance certification, or security certification from this limited run.

Recommended follow-up

  1. Confirm the approved font set and fallback policy with the project owner.
  2. Update only the conflicting typography assertions or implementation after that decision; rerun the two typography scripts.
  3. Run the database-backed smoke test only against an explicitly isolated test database after confirming its URI and reseed behavior.
  4. For broader assurance, add or run non-destructive API integration tests and real browser checks as separate, clearly identified test activities.

7. Test Execution Procedure and Sign-off

  1. Use the project repository and the same dependency/runtime environment used for this execution.
  2. Run only the existing scripts listed in Section 3 using Node.js.
  3. Compare each assertion with its documented expected result and retain the console output as execution evidence.
  4. Resolve F-01 through F-03 based on the agreed typography requirement, then rerun the relevant existing tests.
  5. Record any later integration/browser tests separately; do not merge unexecuted cases into the passing count.
