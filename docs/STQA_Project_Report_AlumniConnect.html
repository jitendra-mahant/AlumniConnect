INTRODUCTION

1.1 Overview of Software Testing and Quality Assurance

In contemporary computer engineering and software development lifecycles, Software Testing and Quality Assurance (STQA) represents the fundamental discipline responsible for ensuring that a software product complies with established functional specifications, satisfies rigorous non-functional constraints, and operates with verified reliability, security, and performance. Software Quality Assurance (SQA) is an umbrella, process-oriented discipline defined by IEEE Standard 730 as "a planned and systematic pattern of all actions necessary to provide adequate confidence that an item or product conforms to established technical requirements."

Conversely, Software Testing is the destructive, analytical, and execution-oriented subset of quality control aimed at discovering defects, identifying deviations between expected and actual behavioral states, and evaluating system capabilities. The primary objectives of software testing include:

  • Defect Detection: Identifying errors, gaps, ambiguities, or missing requirements prior to deployment into live environments.
  • Confidence Building: Providing empirical evidence regarding system stability, security, and fitness for intended institutional use.
  • Risk Mitigation: Preventing costly operational failures, security breaches, unauthorized data exposure, and user dissatisfaction.
  • Standard Compliance: Confirming adherence to industry standards including ISO/IEC 25010 (System and Software Quality Models) and IEEE 829 (Standard for Software and System Test Documentation).

A foundational economic axiom of software engineering is the Cost of Quality curve, initially documented by Barry Boehm. The cost of rectifying a software defect escalates exponentially throughout the software lifecycle. A defect identified during requirement analysis incurs a baseline cost unit of $1 imes$; the same defect discovered during architectural design escalates to $5 imes$, during implementation to $10 imes$, during integration and system testing to $15 imes$, and post-deployment in production to as high as $100 imes$ due to emergency patch development, data corruption remediation, institutional liability, and reputational degradation. Rigorous STQA processes institute early defect prevention through continuous static and dynamic verification.

1.2 Need for Software Testing in Web Applications

Modern full-stack web applications, specifically Single Page Applications (SPAs) communicating via asynchronous RESTful APIs with cloud databases, present unique quality challenges that render ad-hoc manual verification grossly insufficient:

  1. Distributed Architecture & Asynchronous State: The decoupling of client-side user interfaces (React 18) from server-side controllers (Node.js/Express) introduces complex state synchronization, network latency, token invalidation, and race conditions.
  2. Cross-Browser and Multi-Device Heterogeneity: Web applications must deliver identical layout stability, visual contrast, responsive viewport scaling, and DOM execution across Chrome, Edge, Safari, Firefox, and mobile touch browsers ranging from 320px smartphones to 1440px+ desktop workstations.
  3. Stringent Security Vectors (OWASP Top 10): Web endpoints exposed over HTTP/HTTPS are inherently susceptible to Cross-Site Scripting (XSS), NoSQL Injection, Broken Object-Level Authorization (BOLA), mass assignment vulnerabilities, and Cross-Site Request Forgery (CSRF).
  4. Dynamic Data Persistence and Index Collisions: Document databases (MongoDB) enforce schemaless document storage at the engine level; rigorous Mongoose schema validations, unique index constraints, and transaction rollbacks must be rigorously tested to prevent data corruption or partial record insertion.

1.4 Problem Statement

Educational institutions frequently suffer from fragmented, disorganized, and insecure alumni interaction methods. The core challenges addressed by Alumni Connect include:

  • Informal and Ephemeral Channels: Colleges frequently depend on ad-hoc WhatsApp groups, LinkedIn search filters, or outdated physical alumni directories that lack verification, historical archiving, and institutional access control.
  • Absence of Institutional Identity Verification: On general public networks, unverified individuals can claim affiliations with college departments, creating security risks, fraudulent job referrals, and student exploitation.
  • Fragmented Mentorship Workflows: Students seeking guidance on engineering final-year capstones, GATE preparation, higher education abroad, or specific corporate interview tracks have no structured platform to search, connect, and schedule guidance with matching department alumni.
  • Inconsistent User Experience and Accessibility: Prior internal departmental software often suffered from unstandardized fonts, broken light/dark themes, failing contrast ratios, and lack of mobile responsiveness.

2.7 Authentication and Authorization Workflow

The authentication workflow enforces cryptographic guarantees at each stage:

  1. Password Hashing on Registration: Plaintext passwords submitted during registration are processed with bcrypt using a salt factor of 10. The resulting 60-character hash (e.g., $2b$10$...) is persisted; plaintext passwords never touch database disks.
  2. JWT Generation on Login: Upon credential verification via bcrypt.compare(), the server signs a JSON Web Token with HMAC SHA-256 utilizing a secure server secret (JWT_SECRET). The token payload contains { id, role, isVerified } and an expiration lifespan.
  3. Middleware Verification: Protected routes pass through protect middleware, which extracts the token from Authorization: Bearer <token>, invokes jwt.verify(), and attaches the authenticated user record to req.user.
  4. Role Guards: Route-specific middleware (e.g., authorize('admin')) checks req.user.role. If the role does not match, a 403 Forbidden response is immediately terminated prior to controller entry.

      • Invalid Class 2: Malformed email syntax (e.g., user@kkwagh or @kkwagh.edu.in).
  2. Boundary Value Analysis (BVA): Evaluates system behavior at the exact boundaries of input ranges where software defects cluster:
    • Password Length Constraint (Minimum 6 characters):

    • Graduation Year Constraint:

3.4.2 White-Box Testing Techniques Applied

White-box testing inspects internal control structures, decision branches, and execution paths:

8.2 Mathematical Definitions of Standard STQA Metrics

Quantitative evaluation is the hallmark of rigorous software testing. The standard mathematical formulas applied in this project are defined below:

1. Defect Density (DD)

Measures the concentration of defects per unit size of software code, typically expressed per Thousand Lines of Code (KLOC):

$$ ext{Defect Density (DD)} = rac{ ext{Total Number of Confirmed Defects}}{ ext{Total Lines of Code in KLOC}}$$

2. Test Execution Rate (TER)

Measures the percentage of planned test cases that have been executed to date:

$$ ext{Test Execution Rate (TER)} = left( rac{ ext{Number of Executed Test Cases}}{ ext{Total Number of Planned Test Cases}} ight) imes 100%$$

3. Test Pass Percentage (TPP)

Measures the proportion of executed test cases that resulted in a verified PASS status:

$$ ext{Test Pass Percentage (TPP)} = left( rac{ ext{Number of Passed Test Cases}}{ ext{Total Number of Executed Test Cases}} ight) imes 100%$$

4. Requirements Traceability Coverage (RTM Coverage)

Quantifies the extent to which functional and non-functional requirements are covered by test cases:

$$ ext{Requirements Coverage} = left( rac{ ext{Number of Requirements with Associated Passing Tests}}{ ext{Total Number of Documented Requirements}} ight) imes 100%$$

5. Defect Removal Efficiency (DRE)

Measures the efficiency of the testing team in eliminating defects prior to production release:

$$ ext{Defect Removal Efficiency (DRE)} = left( rac{D_{ ext{pre}}}{D_{ ext{pre}} + D_{ ext{post}}} ight) imes 100%$$
where $D_{ ext{pre}}$ = defects found during testing, and $D_{ ext{post}}$ = defects reported in production.

6. Mean Time to Detect (MTTD) & Mean Time to Resolve (MTTR)

MTTD measures average duration elapsed between defect introduction and discovery. MTTR measures average elapsed time between defect logging and verified closure.

9.1 Defect Identification and Logging Workflow

Defect management is the systematic process of discovering, recording, analyzing, triaging, and resolving flaws within software systems. In the Alumni Connect project, defect logging adhered to strict academic documentation standards:

  • Defect Identifier: Unique alphanumeric code (e.g., DEF-01, DEF-02).

9.3 Root Cause Analysis (RCA)

To prevent recurring defect patterns, two analytical Root Cause Analysis techniques were utilized:

9.3.1 The "5 Whys" Technique (Applied to DEF-03: Font Switching Bug)

  1. Why did selecting "Times New Roman" fail to change application typography?
    Answer: Because the font on the page elements remained Arial.
  2. Why did page elements remain Arial?
    Answer: Because the body and heading CSS rules in index.css were hardcoded to font-family: Arial, Helvetica, sans-serif.
  3. Why was Arial hardcoded in index.css?
    Answer: Because early font standardization passes added hardcoded font stacks to eliminate unapproved web fonts (such as Inter and Roboto).
  4. Why wasn't the dynamic custom property used instead?
    Answer: The CSS rule author had not coupled the static font standardization mandate with the reactive --app-font-family theme variable.
  5. Root Cause: Lack of architectural alignment between global font standardization rules and runtime theme provider variables.
    Corrective Action: Unified index.css and Tailwind configuration to strictly inherit from var(--app-font-family).

9.5 Alumni Connect Domain-Specific Vulnerabilities and Mitigation

  1. NoSQL Operator Injection: Attackers submitting JSON objects like {"email": {"$gt": ""}} to bypass authentication.
    Mitigation: Configured express-mongo-sanitize middleware which recursively strips any keys containing $ or . from req.body, req.query, and req.params.
  2. Broken Object Level Authorization (BOLA): Malicious users changing URL parameter IDs to alter other users' profiles or guidance records.
    Mitigation: Enforced identity checks in controllers: if (profile.user.toString() !== req.user.id && req.user.role !== 'admin') return res.status(403).
  3. Cross-Site Scripting (XSS) in Q&A Forums: Malicious users injecting <script> payloads in question descriptions.
    Mitigation: React's virtual DOM engine treats JSX children as strings, escaping HTML characters automatically. Backend input validation also sanitizes HTML entities.

9.6 Corrective Action Protocols

Whenever a defect is logged in the project repository:

  • Isolation: A dedicated git branch is spawned to isolate the defect fix.
  • Test-First Reproduction: A failing test assertion is written to mathematically reproduce the defect before modifying production code.
  • Patch & Verify: Code is patched until the reproduction test passes.
  • Full Regression Pass: Complete test suites (testFontSelectorAndTypography.js, testSidebarControlsAndResponsiveness.js, npm run build) are re-executed before merging into the main branch.

10.3 Known Limitations

While the application exhibits high functional stability, the following technical limitations must be acknowledged:

  1. Local Development Mailer: The current email notification service operates via local simulation and development Nodemailer transports. Under production deployment, a dedicated institutional SMTP relay (e.g., SendGrid, AWS SES) with DKIM/SPF DNS records must be configured.
  2. WebSocket Concurrency Ceiling: Real-time Socket.IO synchronization is configured for single-node in-memory adapter execution. Scaling to thousands of simultaneous campus users will necessitate a distributed Redis pub/sub adapter.
  3. Single Institutional Domain Constraint: The current regex validation explicitly locks registration to @kkwagh.edu.in. Extending the platform to partner colleges or alumni with legacy domains will require an administrative domain whitelist table.

10.4 Unverified Functionality

In accordance with academic integrity guidelines, the following capabilities have not yet undergone automated regression verification:

Appendix E: Comprehensive Glossary of STQA Terminology

BVA (Boundary Value Analysis):
A black-box test design technique in which test cases are designed based on boundary values.
Cyclomatic Complexity:
A structural software metric that measures the number of linearly independent paths through a program's source code.
Defect Density:
The ratio of confirmed software defects relative to the size of the software module, usually expressed per KLOC.
EP (Equivalence Partitioning):
A black-box testing method that divides the input domain into partitions of data from which test cases can be derived.
FOUC / FOFT:
Flash of Unstyled Content / Flash of Faux Text occurring during client-side hydration before theme stylesheets initialize.
JWT (JSON Web Token):
A compact, URL-safe means of representing claims to be transferred between two parties, signed with a cryptographic key.
RACI Matrix:
A responsibility assignment matrix mapping roles across Responsible, Accountable, Consulted, and Informed.
RTM (Requirements Traceability Matrix):
A grid document linking user requirements with their corresponding test cases to verify test coverage.
STLC (Software Testing Life Cycle):
A structured sequence of activities conducted by the testing team to ensure software quality requirements are fulfilled.
WCAG 2.1 AA:
Web Content Accessibility Guidelines Level Double-A standard requiring minimum 4.5:1 text contrast for accessible design.
